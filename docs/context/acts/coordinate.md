**场景台词（知识权威）**：任务「{{title}}」：{{goal}}｜{{count}} 条需求（{{open}} 条进行中）｜{{pending}} 条待受理提案。这一层你只做三件事：**派发、串行受理、过两道门禁**；其余需求的分析/计划/开发可异步并行。

**阶段策略（coordinate_common）**：先受理提案（`proposal.accept`），再过门禁（`gate.approve` / `gate.reject`），再派发（`requirement.dispatch`），最后 `coordinate.submit` 收口进盘点。

**阶段策略（guide_hint，map-guide 组）**：现场规则（field rules）按章节索引——每条规则的标题与摘要在菜单提示行给出，**正文已全部归位到 `docs/context/` 与 `docs/design/`**（本章见下方「协调层语义」节，其余按幕分列）；guide 模式下里程碑动作只能由人从菜单点选。

**人机门禁拒绝（guide_human_blocked，知识权威）**：`proposal.accept` / `gate.approve` / `coordinate.submit` / `verify.submit` / `review.note` 是 pass 型动作，受人类动作门禁保护——guide 模式下只能由人从菜单点选（回复索引 → `ygg.choice_selected`）；直接单发一派发永远被拒（`[REJECTED:ACTION]`），主状态不变。正确做法：把完整 pendingChoice 文本交给用户并等待索引，绝不代按。

**goal / guide 决策权（完整判据）**：

- 只有 Mod 解释 `play.mode`：runtime `settings.play.mode` 覆盖 `data/config.json` 静态缺省，host CLI 不读不解释。`--drive stdin|cmd:<path>|none` 只是宿主输入通道，与模式正交；goal 不依赖外部命令，删除该命令不会破坏 goal。
- `guide`（默认）的五个里程碑只收菜单票，直发始终拒绝；`*.reject` 不在票据门内，因为它们不产生通过效果，是唯一纠正通道。`goal` 中主代理读完整回执后自行派发，不是自动选 1、不经外部脚本，pendingChoice 仍完整打印且证据标准不变。
- 用户当次授权后可 `config.set play.mode=goal`；Mod 叙述 `handover_goal`（委托范围/证据不变/Closing review 须交代）或 `handover_guide`（决策权归还人），菜单只提供切向另一模式的边。
- 运行时 goal 必须逐局 `config.set goal.authorization=<单行说明>`（trim 后非空、≤200、无换行；空值显式清除）。每批结算与退役前的 `review.note` 都检查；缺失则叙述阻断、不写 ending、不前进。静态 goal 预设是仓库 owner 常设配置，不在检查范围；切回 guide 不查，resume 保留记录。该记录只证明登记了一句话，绝不证明是用户亲口授权，不能当身份证据。

**门禁与批边界（执行判据）**：`proposal.accept` 只按阶段推进——analysis→planning、plan→plan_gate、development→accept（交付同时释放泳道）；`gate.approve` 使 plan_gate→ready、accept→done。`gate.reject` 都回 planning：plan reject 置 `plan_ok=false` 须新计划；accept reject 保持旧值，未 amend 回 ready 重新开发，已 amend 因 plan_ok 失效停 planning。approve 前硬查 `gate_rev==req.rev`（amend 后旧批准 stale）及 accept 的 artifacts 非空；summary-only 不受理。

`coordinate.submit` / `verify.submit=true` / `review.note` 共享关闭前置：0 pending proposals、0 running jobs、0 未解冲突，且所有需求 done 或 split/merged/dropped 的后继全 done。`coordinate.submit` 仅在 coordinate 可用，成功写 settle、`verify.passed=false` 并清本批 settlement 键（settings 预登记保留）；`verify.submit=false` 在 `gates.require_all_green=true` 时打回 coordinate 并清 settlement 键。

**入口**：`run.begin`。**必做**（循环直到队列 drain）：受理 → 门禁 → 派发。**出口**：全部需求终态、0 待受理提案 / 0 运行 job / 0 未解冲突后，`coordinate.submit` → 盘点幕（`[COORDINATION DONE]`，run.batch 记批边界）。

**菜单语义对照**：`requirement.dispatch`（按就绪序派发）、`proposal.accept`（串行受理）、`gate.approve`/`gate.reject`（过/打回门禁）、`coordinate.submit`（批边界）、`requirement.list`（看板）、`map.show`、`config`。

**prompts.coordinate 语义**：下一步问题只保留动作名——「受理提案、过门禁、派发，还是收口进盘点（coordinate.submit）？」

## 协调层语义（原 playbook `run_machine` 章，2026-11-15 原样归位）

> 本节自 Mod 的 `data/playbook/ch4-run-machine.json` 逐条搬入，**未改写**——保真优先。
> 其中 `machine.turn-cut` / `machine.pipeline-states` 的实现依据见
> [../../design/kernel/state-machine.md](../../design/kernel/state-machine.md) §2.9。

- **`machine.goal-authorization`**（must）：goal authorization is a **run-level self-declared record**: `config.set goal.authorization=<one-line note>` writes `settings.goal.authorization` (trimmed, ≤ 200 characters, no newline; an empty value clears it explicitly). Only runs that entered goal **at runtime** (`settings.play.mode=goal`) are checked before `review.note` closes: a missing record blocks with a narrative line, writes no `ending` and does not advance; a static `goal` preset in `data/config.json` is the repository owner's standing configuration and is **out of scope** (otherwise the all-1 smoke walk would break). Switching back to guide is not checked, and resume keeps the record. The record only proves "a sentence was registered", not that the user said it — never claim it as identity proof, and it never enters `agent.summary`.
- **`machine.coordinator-chain`**（must）：The coordinator is a **live self-loop** — the kernel FSM has exactly one true transition, `live → retired` (R1): the run opens in the charter act (`run.phase=="charter"`, charter trio via `charter.set`) → `run.begin` opens the standing coordinate act (`run.phase==""`, self-loop: dispatch / serial acceptance / both gates / conflicts) → `coordinate.submit` (queue drained) enters the settle act (`run.phase=="settle"`, four items linearly: `verify.submit` → `settlement.evolution` → `settlement.sessions` → `settlement.todo`) → four items complete auto-advances to the release act (`run.phase=="release"`, R9 effect, no event spent) → `release.confirm` / `release.skip` declare the batch's develop→master outcome → `review.note` settles the batch (`run.phase=""`, `run.batch+1`, back to coordinate) or, with `run.retire` armed, stamps the one true transition to `retired`. `verify.submit=false` sends the whole batch back to coordinate (settlement and release keys cleared).
- **`machine.pipeline-states`**（must）：There is one requirement pipeline per requirement. Stored truth is exactly **2 states** (`req.<i>.status`): `open` / `done` — everything else is derived, never stored; `split` / `merged` / `dropped` are values of the `closed_reason` field (R11), not states. Inside `open` the requirement walks nine micro-states derived by the single-source judge `req_phase()` (menus / render / beats legend all read it — no second copy anywhere): draft(立项) → planning(计划中) ──proposal.submit(plan)──▶ plan_gate(计划门禁) ──gate.approve──▶ ready(待开发) ──requirement.dispatch(+lane)──▶ developing(开发中) ──proposal.submit(development)──▶ dev_review(交付受理) ──proposal.accept──▶ accept_gate(验收门禁) ──gate.approve──▶ integrating(集成) ──integration.confirm──▶ done(完成, terminal). Three push-back paths (`proposal.reject` on a development delivery / `gate.reject` on the accept gate / `integration.reject`) land uniformly in ready (R6: `plan_ok` kept, `job=""`, lane released); `gate.reject` on the plan gate returns to planning with `plan_ok=false`. The two overlay markers (`blocked` / `stale`) stack on top of the phase display and are not states; `analyzing` survives only as a legacy-save compatibility value.
- **`machine.terminal-states`**（must）：The old side states are demoted (剧情双层重写): `split` / `merged` / `dropped` are now values of the `closed_reason` field on a closed (`done`) row (R11 — a closed reason, not a state); the two marker overlays stay display-only: `blocked` (unresolved conflict or needs_amend, cleared by `requirement.resolve` / `requirement.amend`) and `stale` (a proposal whose rev is outdated, cleared automatically once a rebase proposal lands).
- **`machine.coordinator-scope`**（must）：The coordinator does exactly four things — dispatch (requirement.dispatch), accept proposals serially (proposal.accept / proposal.reject), pass the two mandatory gates (gate.approve / gate.reject), and walk each batch boundary (coordinate.submit → the settle act's four items → release.confirm / release.skip → review.note batch settle or retire); it never carries development itself — the feature→develop integration of a requirement belongs to its development executor (`integration.confirm` / `integration.reject`) — and it may never bypass a gate.
- **`machine.requirement-granularity`**（must）：Runtime pointer: `docs/context/acts/coordinate.md` act 1 owns requirement granularity — merge adjacent work first, the three exceptions, the cannot-merge description reason and the three-question check. Do not file a new adjacent requirement from this summary alone.
- **`machine.plan-gate`**（must）：The plan gate (`req.gate=plan`) fires when a plan proposal is submitted (剧情双层重写: gate-on-submit — the plan side has no proposal.accept hop); approve → `plan_ok=true` (the ready act, the only phase that may dispatch into development; the reactive auto-dispatch may continue into developing in the same turn); reject → back to planning with `plan_ok=false`, `rev+1` and the feedback written; it validates `gate_rev == req.rev` (otherwise stale, approval is not allowed).
- **`machine.accept-gate`**（must）：The accept gate (`req.gate=accept`) fires after the main agent accepts the development proposal (the executor delivered); approve → the integrating act (`integrating=true`, gate cleared) — done is NOT granted here, the executor still has to land `integration.confirm` with `develop@<sha>` evidence; reject → the ready act (`plan_ok` keeps its value: not amended → back into the development queue; amended → `plan_ok` was already invalidated → planning, must be replanned); it validates `gate_rev == req.rev` and requires non-empty `artifacts` — a summary-only completion claim is not accepted.
- **`machine.accept-vs-gate`**（must）：accept means the executor self-checked and delivered; it does not mean the main agent has accepted. Only gate.approve is the verification.
- **`machine.gate-not-skippable`**（must-not）：A requirement sitting on the plan / accept gate (`req.gate ~= ""`) cannot be dispatched, accepts no new proposal and cannot be skipped; even automatic advancement (`--drive cmd:…`) runs one `gate.approve` per gate — only the index comes from the external decision command.
- **`machine.closeout-criteria`**（must）：The closeout criteria = `req_all_done()` (including successors of split/merged being all done) + 0 pending proposals + 0 running jobs + 0 conflicts.
- **`machine.batch-maintenance`**（must）：An unarmed batch settle (`review.note`) **auto-appends the next batch's docs-maintenance requirement**: after the `[BATCH n SETTLED]` narration, the same handler transaction adds one open/draft requirement (canonical title 「维护更新 docs wiki（上批收口）」) whose description carries the per-file wiki update guidance over the r2 doc tree (`docs/README.md` index; `docs/context/*` decisions/vocabulary; `docs/design/*` topic files per the batch's touched surface; the two thin-shell maps; wiki-governance's three duties). Dedup: skip the append when the register already holds an open, non-bypassed row carrying the `req.<i>.maintenance` marker or the exact canonical title; a full register also skips. The append is best-effort and **never fails the settlement** — it narrates (`[MAINTENANCE REQ SKIP]`), it never refuses. The retired path (`run.retire` armed → `[ENDING`) appends nothing. The appended draft is never auto-dispatched (draft rows carry no mark) — the main agent dispatches it in the next coordinate phase, and it blocks the next `coordinate.submit` until done: the per-batch docs cadence.
- **`machine.turn-cut`**（must-not）：Runtime projection of `docs/design/kernel/state-machine.md` §2.9: do not add an effect that renders or chooses, needs external evidence, or passes a human gate; do not bypass the declared draft→planning merge or the fixed exec/actor tail order. The specification owns the full protocol and refusal checks; violating it produces rejected payloads, nondeterministic replay, or a second decision bypass.
