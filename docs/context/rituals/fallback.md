# 无 egg 执行本章（无 mod 降级路径）
> **id** rituals/fallback · **幕** all（无 egg 环境） · **触发** 未安装 egg / mod 时的每一次推进
> **读不到代价** silent-drift（无机器 fail-closed 拦截，纪律靠人与会话自律；漏读即静默降级）
> **ver** 000000

不安装 egg / mod 时，本工作流仍可运行——**context 树（含本文）就是完整的工作流底座**：

1. **流程语义**：按 [acts/](../acts/) 的五幕顺序与每幕「入口/必做/出口」人工执行；需求九幕与两道门禁的语义不变（立项 → 计划 → 计划门禁 → 开发 → 交付受理 → 验收门禁 → 集成 → 完成）。
2. **动作名的落地**：`charter.set` = 在会话中写下章程三件套并确认；`requirement.add/dispatch` = 维护需求清单（标题/描述/依赖/状态），按就绪序派发子代理；`proposal.accept` / `gate.approve` = 主会话逐条审阅子代理交付并明示受理/过门禁；`coordinate.submit` = 宣告本批需求全部终态；`verify.submit` = 记录本批验证证据；`settlement.*` = 写下演进登记、会话清理、待办清理三项声明；`release.confirm/skip` = 记录合并 SHA 与批次 tag；`review.note` = 写复盘（lesson|score）。
3. **文案行为可预知**：每个动作「会说什么、拒绝时说什么」查 [copy/README.md](../copy/README.md)（七域索引 + 协议前缀归属）；派发仪式查 [dispatch.md](dispatch.md)；清理政策查 [cleanup.md](cleanup.md)。
4. **三个缺口（明示，不伪装）**：无 egg 时缺少的是——① **工具监控状态**（没有状态机自动判定微状态/就绪序/拒绝面，由主会话自律核对）；② **记录历史**（没有事件日志与自动存档，历史由会话 transcript 与 git 承担）；③ **强制流程合规**（门禁不再由机器 fail-closed 拦截，主会话必须按本文与 AGENTS.md 自律执行，评审者按同一清单核验）。
5. **禁止降级的项**：即使无 egg，「派发 → 提案 → 两道门禁 → 批结算」的顺序与「每步真实动作 + 核验」的证据标准**不降低**——降级的是工具，不是纪律。
6. **需求级九幕的人工执行**：无 egg 时每条需求同样走九幕，由主会话用一张需求清单手工跟踪——每行记「需求 id / 标题 / 依赖 / 当前幕 / 泳道分支 / 证据链接」。逐幕落地：① 立项 = 写清标题/描述/依赖并过合并判据；② 计划中 = 派子代理出计划稿并收回；③ 计划门禁 = 主会话（或人）明示「计划过/打回」；④ 待开发 = 计划已过、等泳道空位（无机器调度，主会话自律排队）；⑤ 开发中 = 子代理实现并交回工件（含 develop@<sha>，集成需求）；⑥ 交付受理 = 主会话逐条审阅并明示「受理/打回」；⑦ 验收门禁 = 人核验证据后明示「验收过/打回」；⑧ 集成 = 执行者已 no-FF 并入 develop，主会话核验 SHA 后标记完成；⑨ done = 终态入册。三道打回统一回「待开发」；rev stale 概念退化为「交付是否基于最新需求描述」的人工核对。每幕该说什么、拒绝时说什么仍查 [../copy/requirements.md](../copy/requirements.md)，各幕动作与证据以 [../req-acts/](../req-acts/) 为准——缺的只是机器的微状态判定、事件日志与 fail-closed 拦截。
